Singleton

Constant Function
Mathematical Definition
$$f(x) = c \quad \forall x$$
$$f(1) = c, \quad f(2) = c, \quad f(99) = c$$
$$\text{addr}(f(1)) = \text{addr}(f(2)) = \cdots = \text{addr}(f(n)) = \text{addr}(c)$$
The uniqueness condition — there exists exactly one instance at all times: $$\exists! \, c \in \mathcal{O} \quad \text{such that} \quad f(n) = c \quad \forall n$$ The symbol $\exists!$ means "there exists exactly one." Any mutation to $f(i)$ is immediately visible through $f(j)$ — because they are the same object.
π

Think of it like the number π. No matter where in mathematics you reference π, it is always the same value at the same conceptual address. You never create a "new π" — you always get the one that already exists.

Exercises
Exercise 01
Basic Singleton
Imagine your app connects to a database. Every time a new connection is created, it costs time and memory. A Singleton ensures only one connection is ever made.
Your task: Create a DatabaseConnection class. No matter how many times someone calls it, it should return the exact same object.
db1 = DatabaseConnection()
db2 = DatabaseConnection()

print(db1 is db2)  # Should print: True
💡 Hints
Python classes have a special method __new__ that runs before __init__. This is where you control whether to create a new object or return the existing one.
Store the single instance as a class variable like _instance = None.
Check: if _instance is None → create it. Otherwise → return it.
Exercise 02
Thread-Safe Singleton
What if two parts of your app try to create the Singleton at the exact same time? You could end up with two instances. This exercise fixes that.
Your task: Extend Exercise 1 so it's safe when multiple threads run simultaneously.
💡 Hints
Import threading and create a Lock object at the class level.
Wrap your instance-creation logic inside with lock: to block other threads until the first one finishes.
This is called "double-checked locking" — check if _instance is None before and after acquiring the lock for efficiency.

Factory Method

Mapping Function
Mathematical Definition
$$f : K \rightarrow \mathcal{T}$$
$$f(k) = T_k() \quad \text{where} \quad T_k \in \mathcal{T}$$
$$f(\text{"dog"}) = \text{Dog()}, \quad f(\text{"cat"}) = \text{Cat()}, \quad f(\text{"bird"}) = \text{Bird()}$$
$f$ is a total function — every valid key maps to exactly one type: $$\forall k \in K, \quad \exists! \, T_k \in \mathcal{T} \quad \text{such that} \quad f(k) = T_k()$$ Unlike Singleton, every call produces a fresh object: $$\text{addr}(f(k)_1) \neq \text{addr}(f(k)_2)$$ The caller only knows $K$ (the keys). The factory owns the knowledge of $\mathcal{T}$ (the types). This decoupling is the core value.
🍔

Think of it like a vending machine. You press a button (key $k$), the machine internally knows which product to dispense (type $T_k$), and gives you a fresh item. You never reach inside the machine yourself — you just press the button.

Exercise 03
Animal Factory
You're building a virtual pet app. Depending on the user's choice, you need to create a different animal. You don't want the rest of your code worrying about which animal class to use.
Your task: Create Dog, Cat, and Bird classes, each with a speak() method. Write a factory that returns the right one based on a string.
animal = AnimalFactory.create("dog")
animal.speak()  # Woof!

animal = AnimalFactory.create("cat")
animal.speak()  # Meow!
💡 Hints
Use a dictionary to map strings to classes: {"dog": Dog, "cat": Cat}. This is cleaner than a long if/elif chain.
Raise a helpful ValueError if the animal type isn't recognized.
The factory can be a class with a @staticmethod or just a plain function — either works.
Exercise 04
Payment Factory
You're building a checkout system. Users can pay by Credit Card, PayPal, or Crypto. Each has a different pay(amount) method, but the rest of the app shouldn't care which one is being used.
Your task: Build CreditCard, PayPal, and Crypto classes, each with a pay(amount) method. Write a factory that returns the right one.

Abstract Factory

Vector-Valued Function
Mathematical Definition
$$f : F \rightarrow \mathcal{T}_1 \times \mathcal{T}_2 \times \cdots \times \mathcal{T}_n$$
$$f(k) = (T_1^{(k)}(),\ T_2^{(k)}(),\ \ldots,\ T_n^{(k)}())$$
$$f(\text{"dark"}) = (\text{DarkButton()},\ \text{DarkCheckbox()},\ \text{DarkMenu()})$$
The consistency condition — all objects in the output tuple must belong to the same family $k$: $$\forall i \in \{1, \ldots, n\}, \quad T_i^{(k)} \in \mathcal{F}_k$$ You can never get a DarkButton paired with a LightCheckbox. Compared to Factory Method: $$\text{Factory Method}: \quad f(k) = T_k() \quad \text{(scalar output)}$$ $$\text{Abstract Factory}: \quad f(k) = (T_1^{(k)},\ \ldots,\ T_n^{(k)}) \quad \text{(vector output)}$$
🛋

Think of it like ordering a matching furniture set. You pick the brand (family $k$), and you receive a sofa, table, and lamp that all match. The store guarantees they are from the same collection — you could never accidentally get a modern sofa with a Victorian lamp.

Exercise 05
UI Theme Factory
Your app supports Dark and Light themes. Each theme has its own version of a Button and Checkbox. When the user switches themes, everything must update consistently.
Your task: Build a DarkThemeFactory and LightThemeFactory, each producing matching Button and Checkbox objects.
factory = DarkThemeFactory()
button = factory.create_button()
checkbox = factory.create_checkbox()
button.render()    # Dark Button
checkbox.render()  # Dark Checkbox
💡 Hints
Start by defining abstract base classes: ThemeFactory, Button, Checkbox using Python's abc module.
Each concrete factory (DarkThemeFactory) implements the abstract factory and returns its own version of each widget.
Client code should only ever talk to the abstract factory — it never imports DarkButton directly. That's the whole point.

Builder

Function Composition
Mathematical Definition
$$g_i : S \rightarrow S \quad \text{(each step is a state transformation)}$$
$$f = g_n \circ g_{n-1} \circ \cdots \circ g_2 \circ g_1$$
$$s_1 = g_1(s_0), \quad s_2 = g_2(s_1), \quad \ldots, \quad s_n = g_n(s_{n-1})$$
The final .build() is a projection function $\phi$ that extracts the finished object: $$\phi : S \rightarrow \mathcal{O}, \qquad \text{result} = \phi(s_n) = \phi(f(s_0))$$ Each step $g_i$ only modifies one aspect of the state: $g_i(s) = s \oplus \delta_i$. Note that composition is generally not commutative: $$g_2 \circ g_1 \neq g_1 \circ g_2 \quad \text{in general}$$
🏭

Think of it like an assembly line. Each station $g_i$ adds one component. The car starts as an empty frame $s_0$, gets an engine at $g_1$, wheels at $g_2$, paint at $g_3$. The final inspection $\phi$ signs it off as a complete car. No station knows or cares what the others do.

Exercises
Exercise 07
Pizza Builder
A pizza can have many combinations: size, crust, and toppings. Instead of a constructor with 10 arguments, a Builder lets you add what you want step by step.
Your task: Create a PizzaBuilder that chains methods together and ends with .build().
pizza = PizzaBuilder() \
    .set_size("large") \
    .set_crust("thin") \
    .add_topping("cheese") \
    .add_topping("mushrooms") \
    .build()

print(pizza)  # Large thin-crust pizza with: cheese, mushrooms
💡 Hints
For chaining to work, each method must return self at the end — this is the $g_i(s) = s \oplus \delta_i$ step in code.
add_topping() should append to a list, so it can be called multiple times.
build() should return a Pizza object (or formatted string), not the builder itself — this is the $\phi$ projection.
Exercise 08
SQL Query Builder
Writing raw SQL strings by hand is messy and error-prone. A Query Builder lets you construct them cleanly, piece by piece.
Your task: Build a QueryBuilder that constructs a SQL string step by step.
query = QueryBuilder() \
    .select("*") \
    .from_table("users") \
    .where("age > 18") \
    .build()

print(query)  # SELECT * FROM users WHERE age > 18
💡 Hints
Store each part (select, table, condition) as instance variables — these are your state $s$.
build() assembles them in the correct order using an f-string or join() — this is the $\phi$ projection.
What if .where() is never called? Make sure build() handles optional parts gracefully.

Prototype

Copy Function
Mathematical Definition
$$f : \mathcal{O} \rightarrow \mathcal{O}$$
$$f(x) = x' \quad \text{such that} \quad \text{val}(x') = \text{val}(x) \quad \text{and} \quad \text{addr}(x') \neq \text{addr}(x)$$
The independence condition — for any mutation $m$ applied to the clone $x'$: $$m(x') \Rightarrow \text{val}(x) \text{ unchanged}$$ This must hold recursively for all nested objects $x_i$ inside $x$: $$\text{shallow copy}: \quad \text{addr}(x'_i) = \text{addr}(x_i) \quad \text{(independence violated)}$$ $$\text{deep copy}: \quad \text{addr}(x'_i) \neq \text{addr}(x_i) \quad \forall i \quad \text{(independence holds)}$$ Chained cloning always produces independent objects: $$f(x) = x', \quad f(x') = x'', \quad \text{addr}(x) \neq \text{addr}(x') \neq \text{addr}(x'')$$
🧬

Think of it like biological cell division. A cell $x$ splits into $x'$ — same DNA (values), but a completely separate physical cell (address). Damage to $x'$ does not damage $x$. They share an origin but are now fully independent living entities.

Exercises
Exercise 09
Basic Clone
You have a Car object that took a lot of setup. You want a second car that's almost identical — just a different color. Instead of rebuilding from scratch, you clone it.
Your task: Create a Car class with a clone() method. Verify that changing the clone doesn't affect the original.
car1 = Car("Toyota", "red", "V6")
car2 = car1.clone()
car2.color = "blue"

print(car1.color)  # red  ← original unchanged: val(x) unchanged
print(car2.color)  # blue ← clone changed:    m(x') applied
💡 Hints
Python's copy module has two options: copy.copy() (shallow) and copy.deepcopy() (deep). Use deep copy — it satisfies the full independence condition.
Your clone() method can simply return copy.deepcopy(self).
Test it with a nested attribute (like a list of features) to see exactly why deep copy matters over shallow.
Exercise 10
Prototype Registry
You have a catalog of pre-built shapes. Users pick one from the catalog and customise their own copy — without ever touching the original template.
Your task: Build a ShapeRegistry that stores prototype shapes. Users request a clone by name and modify it freely.
registry = ShapeRegistry()
registry.register("circle", Circle(radius=5, color="red"))
registry.register("rectangle", Rectangle(width=10, height=4, color="blue"))

my_circle = registry.get_clone("circle")
my_circle.color = "green"

original = registry.get_clone("circle")
print(original.color)  # red ← registry untouched: val(x) unchanged
💡 Hints
The registry is just a dictionary: {"circle": <Circle object>}. The values are your prototypes $x$.
get_clone() should return copy.deepcopy(self._prototypes[name]) — never the original. This is $f(x) = x'$.
This pattern is powerful when object creation is expensive (e.g. loaded from a file or database) — you pay the cost once, then clone cheaply.

Pattern Comparison

Pattern Math Type New object each call? Coordinated output? Copies existing?
Singleton Constant $f(x) = c$ Never No No
Factory Method Mapping $f: K \to \mathcal{T}$ Always No (scalar) No
Abstract Factory Vector $f: F \to \mathcal{T}_1 \times \cdots \times \mathcal{T}_n$ Always Yes (family) No
Builder Composition $f = g_n \circ \cdots \circ g_1$ Always No No
Prototype Copy $f(x) = x'$ Always No Yes
